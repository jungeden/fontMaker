# 손글씨 TTF 폰트 생성기

내 손글씨로 완성형 한글 11,172자(가~힣) + 영문 대소문자 + 숫자 + 특수문자까지 담은
TTF 폰트를 만드는 도구. 커닝(kerning)과 힌팅(hinting)까지 자동으로 적용된다.

11,172자를 전부 손으로 쓰는 대신, **모양이 실제로 달라지는 최소 단위(183개)만** 손글씨로
받고, 나머지는 초성/중성/종성 조합 공식으로 자동 조립한다. 영문/숫자/특수문자(94개)는
한글과 달리 조합되지 않으므로 한 칸에 한 글자씩 그대로 받는다.

총 **183(한글 컴포넌트) + 94(영문/숫자/특수문자) = 277칸**만 손글씨로 채우면 된다.

## 원고지 가이드는 자동으로 지워진다

원고지 각 칸의 점선 상자, 번호, 예시 글자, baseline 안내선은 모두 **아주 연한 회색**으로
인쇄된다. 종이에서 보기엔 충분히 진하지만, 전처리 단계(`preprocess.py`)에서 이 밝기보다
밝은 픽셀은 전부 흰 배경으로 자동 처리하기 때문에 스캔한 뒤 사람이 직접 지울 필요가 없다.
실제 손글씨(검은 펜/연필)는 훨씬 어두우므로 영향받지 않는다. 칸을 나누는 검정 실선 테두리만
남아서 `segment.py`가 칸을 나누는 기준으로 쓴다.

한글 칸에는 예시 음절 전체("가", "곽" 등)가 큰 워터마크로 깔려 있어서, 내가 쓰는 자모가
전체 글자 안에서 어느 크기/위치에 있어야 하는지 보면서 쓸 수 있다. 점선 상자 = 실제 쓰기
한계선이라고 생각하면 된다 (상자를 벗어나면 조합했을 때 옆 자모와 겹칠 수 있음).

라틴 문자 칸은 **실선 상자 = 실제 사용 가능한 전체 높이**(위쪽 끝 = ascender, 아래쪽 끝 =
descender)다. 이 상자를 벗어나면 글자가 잘린다. 상자 안의 굵은 가로선이 baseline이고,
대부분의 글자는 이 선 위에 앉지만 g, y, p, q, j 는 이 선 아래(상자 하단까지)로 내려가면 된다.

(만약 그래도 가이드가 스캔 상태에 따라 완전히 지워지지 않는다면, `python app.py template`
실행 시 함께 만들어지는 `output/grid_overlay_page*.png`(격자선만 있는 투명 배경 PNG)를 이용해
직접 손으로 편집한 손글씨 이미지에 격자를 합성해서 올려도 된다.)

## 왜 183개인가 (한글)

- **초성(19개) × 6가지 = 114개** — 받침 유무(2) × 뒤에 오는 모음의 방향(세로형/가로형/복합형, 3)
  에 따라 초성의 폭과 위치가 크게 달라진다. (예: "가"의 ㄱ과 "곡"의 ㄱ은 모양이 다르다)
- **중성(21개) × 2가지 = 42개** — 받침 유무에 따라 모음의 세로 길이가 달라진다.
- **종성/받침(27개) × 1가지 = 27개** — 받침은 항상 글자 하단의 같은 자리에만 오므로
  형태 변화가 없다.

114 + 42 + 27 = **183개**만 쓰면, 유니코드 조합 공식
`코드 = 0xAC00 + (초성인덱스×21 + 중성인덱스)×28 + 종성인덱스` 으로 11,172자를 전부 조합할 수 있다.

## 영문/숫자/특수문자 (94개)

출력 가능한 기본 ASCII 문자 전체(`!` ~ `~`, 공백 제외 94자)를 지원한다. 공백은 글자 모양이
없으므로 폭 값만 자동으로 채워진다.

## 사용법

```bash
pip install -r requirements.txt

# 1) 원고지 PDF 생성 (277칸, 여러 페이지 + 범례 페이지 포함)
python app.py template
# -> output/template.pdf, output/grid_overlay_page*.png, data/manifest.json 생성됨

# 2) 인쇄해서 손글씨로 채운 뒤, 페이지 순서대로 스캔/촬영
#    data/scans/page1.jpg, data/scans/page2.jpg ... 로 저장

# 3) 전처리 -> 컴포넌트 분할 -> 한글 11,172자 자동 조합 + 영문/숫자/특수문자
#    -> 커닝 -> 힌팅 -> TTF 생성
python app.py build
# -> output/MyHandwriting.ttf
```

컴포넌트를 일부만 채워도, 그 컴포넌트로 조합/생성 가능한 글자만 생성된다(나머지는 자동 제외).

## 구조

```
fontMaker
├── data
│   ├── scans/            # 스캔한 원고지 사진 (page1.jpg, page2.jpg ...)
│   ├── glyphs/            # 분할된 컴포넌트 PNG (000.png ~ 276.png)
│   └── manifest.json      # 277개 컴포넌트 정의 (template.py가 생성, segment/compose/latin이 사용)
├── modules
│   ├── hangul.py           # 한글 자모 데이터 + 183개 컴포넌트 목록 + 조합 좌표(zone) 테이블
│   ├── latin.py            # 영문/숫자/특수문자 94개 컴포넌트 목록 + 개별 글리프 생성
│   ├── template.py         # 원고지 PDF 생성 (연한 회색 가이드 + 한글 워터마크 + 라틴 baseline 박스)
│   │                        # + 격자 전용 투명 PNG 오버레이 생성
│   ├── preprocess.py       # 스캔 이미지 보정 (기울기 보정, 연한 가이드 자동 제거, 이진화)
│   ├── segment.py          # 원고지 칸 -> 컴포넌트 PNG 분할 (한글: 빈칸 스킵/baseline 정렬/크기 정규화,
│   │                        #                                라틴: baseline 위치를 유지한 채 그대로 정규화)
│   ├── vectorize.py        # PNG -> 윤곽선(구멍 포함) 검출
│   ├── glyph.py            # 윤곽선 -> 폰트 좌표계 변환 + 베지어 곡선화 (한글용)
│   ├── compose.py          # 183개 한글 컴포넌트로 11,172자 전체를 좌표 기반 조합
│   ├── kerning.py          # 라틴 글자 쌍 자동 커닝 계산 + GPOS kern 피처 적용
│   └── fontbuild.py        # 한글+라틴 글리프 합치기 + 커닝 + 힌팅 -> 최종 .ttf 저장
├── output/                 # template.pdf, grid_overlay_page*.png, MyHandwriting.ttf
├── app.py                  # 전체 파이프라인 실행 (template / build)
├── config.py                # 전역 설정값
└── requirements.txt
```

## 조합 좌표(zone) 튜닝 방법

`modules/hangul.py`의 `ZONE_LAYOUTS` 딕셔너리가 (받침 유무, 모음 방향) 6가지 조합마다
초성/중성/종성이 차지할 사각형 영역을 `(x0, y0, x1, y1)` (1000x1000 기준, y=0이 baseline,
y=1000이 글자 상단)으로 정의한다.

```python
(True, "V"): {                    # 받침 있음 + 세로모음 (각, 닫, 빛...)
    "cho":  (0,   280, 500, 1000),  # 초성: 왼쪽 절반, 아래에서 280~1000
    "jung": (500, 280, 1000, 1000), # 중성: 오른쪽 절반, 아래에서 280~1000
    "jong": (0,     0, 1000, 280),  # 종성: 전체 폭, 맨 아래 0~280
},
```

폰트를 뽑아봤을 때 예를 들어 **받침이 중성과 겹친다** → `jong`의 `y1`(280)을 줄이고,
그만큼 `cho`/`jung`의 `y0`도 같이 올려서 받침 공간을 넉넉하게 만들면 된다. **초성이 너무
작아 보인다** → `cho`의 영역을 넓히면 된다. 코드의 다른 부분은 건드릴 필요 없이 이 표의
숫자만 바꾸면 즉시 반영된다.

각 컴포넌트는 이 zone 안에서 **원본 비율을 그대로 유지한 채(찌그러지지 않게) 최대한
크게 맞춰지고 중앙 정렬**된다 (letterbox 방식). zone의 가로세로 비율과 실제 손글씨의
비율이 달라도 글자가 눌리거나 늘어나지 않는다.

### 특정 자모만 더 세밀하게 보정하고 싶다면

비율 유지 방식만으로도 대부분 자연스럽지만, 손글씨 특성상 어떤 자모는 상대적으로
작아 보이거나(예: ㄱ, ㅣ) 커 보일 수 있다(예: ㅁ, ㅇ). `modules/hangul.py`에 있는 아래
표들로 미세 조정할 수 있다.

```python
# 초성/중성/종성 전체적인 균형 조절
KIND_SCALE = {"cho": 1.0, "jung": 1.0, "jong": 1.0}

# 특정 (종류, 자모)만 배율 조정 - 예: 초성 ㅇ만 8% 키우기
COMPONENT_SCALE = {
    ("cho", "ㅇ"): 1.08,
}

# 특정 (종류, 자모)만 위치 미세 조정 (dx, dy, 폰트 유닛 기준) - 예: 초성 ㅊ를 위로 15만큼
COMPONENT_OFFSET = {
    ("cho", "ㅊ"): (0, 15),
}
```

`("cho", "ㅇ")`과 `("jong", "ㅇ")`은 서로 다른 손글씨 조각(초성 ㅇ vs 받침 ㅇ)이므로 따로
보정할 수 있다.

라틴 문자의 baseline 위치는 `modules/latin.py`의 `BASELINE_RATIO`(= config.py의
ASCENDER/DESCENDER 비율)로 정해진다.

## Kerning(커닝)과 Hinting(힌팅)이란?

**커닝**: 특정 두 글자를 나란히 놓았을 때 생기는 시각적인 간격 차이를 보정하는 것.
예를 들어 활자에서 "AV"를 그냥 이어붙이면 사이에 불필요하게 큰 틈이 생기는데, 커닝으로
이 틈을 좁혀서 다른 글자 쌍과 비슷한 간격으로 보이게 만든다. 이 프로젝트는 라틴 문자
94개의 모든 쌍(약 8,700쌍)에 대해 실제 손글씨 윤곽선을 분석해서, 너무 붙거나 너무 뜬
쌍만 자동으로 보정하는 커닝을 적용한다 (`modules/kerning.py`, 이번 빌드에서 7,330쌍
적용됨). 한글 음절은 전부 같은 폭의 정사각형 칸에 들어가는 전각 문자라서 커닝을
적용하지 않는다 (표준적인 한글 조판 방식).

**힌팅**: 작은 크기(특히 저해상도 화면)에서 글자 획이 흐릿하거나 삐뚤어지지 않게, 폰트
안에 "이 크기에서는 이 획을 픽셀 격자에 맞춰 그려라"라는 지시를 추가하는 작업. 이 지시는
폰트 전용 바이트코드 언어로 작성해야 해서 직접 구현하기는 매우 복잡하지만, 널리 쓰이는
오픈소스 자동 힌팅 도구인 **ttfautohint**가 시스템에 설치되어 있으면 빌드 마지막 단계에서
자동으로 적용된다 (없으면 힌팅 없이 저장하고 설치 방법을 안내한다).

```bash
# ttfautohint 설치 (선택 사항 - 없어도 폰트는 정상적으로 만들어진다)
brew install ttfautohint          # macOS
sudo apt install ttfautohint      # Linux
# Windows: https://freetype.org/ttfautohint/#download
```

## 한계

- 초성 6종류 분류는 실제 정식 폰트 제작사가 쓰는 세밀한 분류(보통 더 많은 변형)보다는
  단순화된 버전이다. 특히 복합모음(과/궈/의 등) 앞 초성은 근사치로 처리된다.
- 컴포넌트는 원본 비율을 유지한 채 zone에 맞춰지므로 찌그러지지는 않지만, 자모마다
  자연스러운 크기 차이(예: ㄱ은 작고 ㅁ은 큼)는 `COMPONENT_SCALE`로 수동 보정해야 한다.
- 라틴 문자의 baseline 정렬은 스캔이 원고지 인쇄 비율과 잘 맞아떨어진다고 가정한다. 스캔이
  심하게 기울어지거나 왜곡되면 g/y/p 같은 글자의 baseline이 살짝 어긋날 수 있다.
- 커닝은 라틴 문자에만 적용되고, 진짜 폰트 제작사 수준의 정교한 곡선 피팅(최소자승 베지어
  피팅)은 구현하지 않았다 (2차 베지어 근사만 사용).
